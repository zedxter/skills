Six months ago, I joined a project and spent my first two weeks asking the same question: "Why does it work this way?"

Nobody knew. The person who made the decision had left. The Slack thread was archived. The code was clever, but it didn't explain itself.

That cost us weeks, not minutes.

Here's the thing I've learned: **undocumented code is a loan you take out against your teammates' time.** The interest compounds with every new hire, every context switch, and every 2 a.m. incident.

Why I now write more docs than I used to:

**1. Future you is a stranger.**
In six months, you won't remember why you chose that workaround. Write it down and you'll thank yourself.

**2. Docs scale you.**
Every question you answer once in writing is a question you never have to answer again. That's leverage.

**3. Writing exposes fuzzy thinking.**
If you can't explain a design in a paragraph, you probably don't understand it well enough yet. Documenting often improves the design itself.

**4. Onboarding gets faster.**
Good docs turn "two weeks of confusion" into "productive by Friday."

**5. Incidents get shorter.**
A clear runbook at 2 a.m. is worth more than the smartest engineer who is asleep.

You don't need a 50-page wiki. Start small:

- A README that actually explains how to run the thing
- A short note on *why* you made a decision, not just what you did
- Comments on the weird parts of the code
- A runbook for the things that break

Keep it close to the code, and update it when the code changes. Docs that go stale are worse than none.

The best engineers I know aren't just great at writing code. They're great at making sure others can understand it.
